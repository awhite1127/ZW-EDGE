# 内置设备接入规范

本文描述当前正式产品中新增或维护内置 Modbus 设备的标准做法。规则以
`DeviceTemplateDefinition`、现有 wired/wireless 定义和运行主链为准，不引入新的设备 DSL、数据库分类字段或协议层抽象。

## 1. 基本原则

拿到新设备协议后，首先尝试用现有模型完整表达：

```text
厂家协议
  -> 设备族归类
  -> ReadBlocks
  -> Fields / Enum / Bit / InvalidRule
  -> summary / show_in_realtime / history_enabled
  -> 必要时 WriteCommands
  -> builtin registry
  -> 真实设备验证
```

普通设备接入不应从修改 `MasterCollector`、`RegisterMapper` 或 `BackendService` 开始。只有真实协议超出通用模型表达能力时，才增加范围明确的设备专属逻辑。

内置设备协议与结构的唯一事实源是 C++ `builtin_device_templates()`。SQLite 只承担运行持久化，以及内置字段 `realtime_display`、`history_enabled` 用户偏好；不要把数据库快照当成内置协议定义。

## 2. 推荐接入流程

1. 获取厂家正式通讯协议和已确认的补充说明，列出寄存器、功能码、数据宽度、字序、倍率、无效值及写操作风险。
2. 判断设备属于 wired 还是 wireless 代码族；这只是源码组织规则。
3. 根据协议选择 FC03 或 FC04，并划分不可跨读的数据区。
4. 设计 `ReadBlocks`，再把每个业务字段绑定到所属区块。
5. 明确字段数据类型、解析器、寄存器数量、字节序/字序、scale、offset、precision 和 unit。
6. 按协议配置 invalid rule、enum 或 bit，不在 Web 中复制单设备解析逻辑。
7. 分别确认 `summary`、`show_in_realtime`、`history_enabled`，不得互相推导。
8. 厂家协议确有受控写操作时，评估并定义 builtin-only `WriteCommands`。
9. 在对应设备族文件中实现定义，并在 `builtin_device_templates.h` 与 `builtin_device_templates()` 注册。
10. 先通过现有模型校验，再核对真实 Modbus 报文、工程量、页面行为和写操作结果。

## 3. wired / wireless 归类

| 设备族 | 放置位置 | 当前示例 |
| --- | --- | --- |
| wireless | `backend/src/model/builtin_wireless_devices.cpp` | R2、R2A、R4 系列 |
| wired | `backend/src/model/builtin_wired_devices.cpp` | RD100、CM-RD100、CM-SF6、CM-WT、EM100、EM100H |

未来明确属于无线终端、无线传感器、中继或现有无线产品体系的设备归入 wireless；其它通过现有 Modbus RTU/TCP 主链直接接入的设备默认归入 wired。

这一区分不进入运行时模型。不要新增 `connection_type`、`device_family`、wired/wireless 数据库字段，也不要根据中文名称自动分类。

## 4. ReadBlocks 设计

- FC03/FC04 必须来自厂家协议，不为代码统一而改成功能码相同。
- 厂家允许时，连续寄存器优先合并，以减少请求数量。
- 厂家明确禁止跨区读取时必须拆分，即使地址相邻。EM100H 的 `realtime_data` 与 `runtime_status` 必须继续作为两个独立区块。
- 小间隔且允许跨读时可合并；跨度大或协议边界明确时拆分为多个区块。
- `start_offset` 与 `register_count` 必须严格来自协议；当前单区块读取数量为 1～125。
- `start_offset` 相对于设备基地址，`field.register_offset` 相对于所属 ReadBlock，不要混用绝对地址。
- `device_address_stride` 表示相邻设备基地址间距，所有读取区块必须落在该跨度内。
- 普通设备继续由 `BlockReadPlan` 和 `MasterCollector` 执行，不增加设备专属轮询循环。

## 5. 字段定义

每个 `DeviceTemplateFieldDefinition` 至少显式确认：

- 稳定、英文、有业务含义且模板内唯一的 `field_key`；
- 中文 `display_name`；
- `read_block_key` 与区块内 `register_offset`；
- `data_type`、匹配的 `parser_id` 和 `register_count`；
- `scale`、`value_offset`、`precision`、`unit`；
- `summary`、`show_in_realtime`、`history_enabled`；
- `display_order`。

按协议需要再设置 `byte_order`、`word_order`、invalid rule、`enum_items`、`bit_index` 和 `realtime_group_id`。正式发布后的 field key 会被历史、偏好和页面引用，除非做了明确的数据兼容处理，否则不要随意改名。

### 5.1 数据类型与解析器

| 数据类型 | 寄存器数 | 解析器 |
| --- | ---: | --- |
| `uint16` | 1 | `scaled_uint16` |
| `int16` | 1 | `scaled_int16` |
| `uint32` | 2 | `scaled_uint32` |
| `int32` | 2 | `scaled_int32` |
| `float32` | 2 | `scaled_float32` |
| `bool` | 1 | `bit_uint16` |

系统还支持 `scaled_high_uint8` / `scaled_low_uint8` 从一个寄存器中解析高/低 8 位，其 `data_type` 仍为 `uint16`。不要增加名称相近但运行时不支持的 parser id。

16 位、8 位和 bit 字段使用 `big_endian + high_word_first`。32 位字段支持：

| byte_order | word_order | 常见排列记法 |
| --- | --- | --- |
| `big_endian` | `high_word_first` | ABCD |
| `little_endian` | `high_word_first` | BADC |
| `big_endian` | `low_word_first` | CDAB |
| `little_endian` | `low_word_first` | DCBA |

必须根据厂家资料或真实报文确认宽度、signed/unsigned、float 和两个寄存器的组合顺序；协议不明确时不要在代码中增加猜测分支。

### 5.2 工程量转换

通用线性转换为：

```text
工程量 = 解码后的原始值 × scale + value_offset
```

- `scale`：厂家规定的倍率；
- `value_offset`：厂家规定的线性偏移；
- `precision`：显示和数据表达精度；
- `unit`：用户看到的工程单位。

线性转换能够表达时，不要新增设备专属 parser。

### 5.3 invalid rule 与质量语义

当前通用 invalid rule 只支持：

- `none`；
- `equal`；
- `greater_or_equal`；
- `less_or_equal`；
- `inside_range`（闭区间）。

规则在解码后的原始值上、应用 scale/offset 之前判断。规则值必须来自厂家协议或已验证设备行为，不要为了统一让不同设备共享同一阈值。

通讯超时、CRC/异常响应属于通讯失败；报文成功但字段命中 invalid rule 属于字段数据无效。后者不能伪装成 Modbus 通讯失败。复杂状态组合不属于当前通用 invalid rule，只有协议确实需要且现有 enum/bit 无法表达时才考虑设备专属处理。

### 5.4 enum、bit 与实时分组

- 寄存器值表示离散状态时优先使用 `enum_items`，不要在 Web 中为单设备手写 value formatter。
- enum 只改变显示文字，数值仍是告警、历史和北向数据的基础；enum 字段要求 scale=1、offset=0、precision=0。
- 状态位使用 `data_type=bool`、`parser_id=bit_uint16`、`register_count=1` 和 0～15 的 `bit_index`。
- bit 字段同样明确中文名称和 0/1 语义，可用 enum 覆盖默认“否/是”显示。
- 启用 `realtime_grouping_enabled` 时，所有实时展示字段都必须绑定现有 `realtime_group_id`；分组只组织实时页面。

## 6. 三项字段能力

三项能力相互独立，新增字段必须逐项作出产品判断：

| 字段 | 产品语义 | 当前消费者 |
| --- | --- | --- |
| `summary` | 关键数据 | 设备摘要、告警候选、MQTT realtime 默认发布 |
| `show_in_realtime` | 实时监控是否展示 | 实时监控页面 |
| `history_enabled` | 是否记录历史 | 历史写入与查询 |

不要把所有字段都设为关键数据。关键数据应代表用户最关心的核心测量或状态；辅助配置、内部运行量、备用寄存器通常不应全部进入摘要、告警和 MQTT。

实时展示选择现场需要持续查看的字段；历史记录选择具有趋势、追溯和报表价值的字段。内部状态、临时值和调试数据没有产品价值时可关闭。禁止恢复 `summary -> realtime/history` fallback。

EM100H 是多区块与能力独立的实际案例：业务字段位于 `realtime_data`，运行/备用区保持独立；当前五个业务字段均实时展示和记录历史，但只有绝缘电阻与剩余电流属于关键数据。

## 7. WriteCommands

WriteCommands 只服务公司维护的 builtin device。自定义设备仍只允许 FC03/FC04，不允许导入命令，也不允许 Web/API 传入 master、任意寄存器和值执行裸 FC10。

只有厂家协议明确、公司能够确认写地址、数量、值/参数范围和风险时才增加命令。优先使用现有 `fixed_values` 或单寄存器 `value_fields`；当前参数类型只有 `uint16` 和 `enum`。

每条命令至少定义：

- 稳定且模板内唯一的 key、非空 name；
- `function_code=16`；
- absolute 或 relative address；
- 1～123 的 `register_count`；
- 数量匹配且互斥的 `fixed_values` 或 `value_fields`。

可选体验元数据：

- `description`：简洁说明操作作用；
- `warnings`：高压、清除数据、长时间运行等真实风险；
- `require_confirm`：危险或会改变设备运行状态时合理启用；
- `confirm_text`：专属确认文案，缺失时 UI 使用通用文案；
- `success_hint`：成功反馈；
- `group`：操作页面的轻量分组，空值进入默认分组。

新增定义会经过 `validate_device_template_write_commands()`。不要增加 float/int32 参数、表达式、bit packing、脚本、多步骤 workflow 或没有真实消费者的元数据。

## 8. 何时允许设备专属逻辑

先尝试以下通用组合：

```text
DeviceTemplateDefinition + ReadBlocks + Fields
+ Enum + Bit + InvalidRule + WriteCommands
```

只有真实协议无法表达时才允许专属实现，例如：

- 读取会消费或清除的特殊记录区；
- 厂家自定义 packed timestamp；
- 多寄存器形成非通用结构；
- 特殊命令执行流程。

EM100 的事件记录、测试记录、packed timestamp 和 event code 是当前允许的专属案例。一个设备出现特殊需求时先保持设备专属实现；第二、第三个真实设备出现相同需求后，再评估通用抽象。

## 9. 通常修改与不应修改的位置

普通 wired 设备通常只修改：

- `backend/src/model/builtin_wired_devices.cpp`；
- `backend/src/model/builtin_device_templates.h`（声明稳定访问函数）；
- `backend/src/model/builtin_device_templates.cpp`（加入 registry）。

普通 wireless 设备将第一项替换为 `builtin_wireless_devices.cpp`，其它相同。

现有模型能够表达时，通常不应修改：

- `MasterCollector`、`RegisterMapper`、`BlockReadPlan`；
- `DeviceTemplateStore`、`BackendService`；
- Modbus RTU/TCP 协议实现；
- Web 通用数据解析和页面主链；
- MQTT payload、历史存储、告警主链。

如果普通设备需要同时修改很多底层模块，应先检查 ReadBlocks、字段解析器和现有能力是否使用正确。

## 11. 带 WriteCommands 的示例

以下命令同样只用于文档。地址和值必须替换为厂家协议确认内容：

```cpp
std::vector<DeviceTemplateWriteCommandDefinition> example_commands()
{
    DeviceTemplateWriteCommandDefinition reset;
    reset.key = "reset_device";
    reset.name = "设备复位";
    reset.description = "使设备重新启动。";
    reset.group = "设备控制";
    reset.function_code = 16;
    reset.has_absolute_register = true;
    reset.absolute_register = 0x2000;
    reset.register_count = 1;
    reset.fixed_values = {0x55AA};
    reset.warnings = {"复位会短暂中断设备采集。"};
    reset.require_confirm = true;
    reset.confirm_text = "确认复位该设备吗？";
    reset.success_hint = "复位命令已发送。";

    DeviceTemplateWriteCommandField mode;
    mode.key = "mode";
    mode.label = "运行模式";
    mode.type = "enum";
    mode.min = 0;
    mode.max = 1;
    mode.has_default_value = true;
    mode.default_value = 0;
    mode.options = {{"手动", 0}, {"自动", 1}};

    DeviceTemplateWriteCommandField delay;
    delay.key = "delay_seconds";
    delay.label = "启动延时";
    delay.type = "uint16";
    delay.min = 1;
    delay.max = 60;
    delay.unit = "秒";
    delay.has_default_value = true;
    delay.default_value = 10;

    DeviceTemplateWriteCommandDefinition configure;
    configure.key = "configure_operation";
    configure.name = "设置运行参数";
    configure.description = "设置运行模式和启动延时。";
    configure.group = "系统设置";
    configure.function_code = 16;
    configure.has_absolute_register = true;
    configure.absolute_register = 0x2100;
    configure.register_count = 2;
    configure.value_fields = {mode, delay};  // 顺序对应连续写入的两个寄存器
    configure.success_hint = "运行参数已写入。";

    return {reset, configure};
}
```

将命令加入真实模板前，必须确保 `validate_device_template_write_commands()` 通过；执行期仍会再次校验用户输入、设备/主站状态、实际地址和 Modbus 结果。

## 12. 不推荐做法

- 不要一个普通设备写一个专属 Collector，也不要一个设备拆一个 cpp 造成碎片化。
- 不要为一个 enum 在 Web 手写 formatter，也不要为简单 scale 写专属 parser。
- 不要跨读厂家禁止跨越的数据区，不要猜测 32 位字序。
- 不要让 summary 隐式控制 realtime/history。
- 不要把所有字段默认设为关键、实时或历史。
- 不要开放裸 FC10，也不要提前建立命令 DSL、脚本或 workflow。
- 不要为代码统一而改变厂家明确不同的 invalid rule。

## 13. 接入检查清单

### 协议

- [ ] 已确认 FC03/FC04、基地址、寄存器数量和不可跨读区。
- [ ] 已确认 16/32 位类型、signed/unsigned、float、byte order 和 word order。
- [ ] ReadBlock 与字段 offset 均按各自相对地址定义。

### 字段

- [ ] key 稳定且模板内唯一，名称、scale、offset、precision、unit 正确。
- [ ] invalid rule 来自协议，通讯失败与字段无效没有混淆。
- [ ] enum/bit 优先使用通用模型。
- [ ] summary、show_in_realtime、history_enabled 已分别确认。

### 写操作

- [ ] 确实需要 builtin WriteCommands，写地址、数量和值/参数已确认。
- [ ] fixed_values/value_fields 数量匹配且定义期校验通过。
- [ ] 风险操作已填写 warning，并合理设置确认文案。

### 代码与验证

- [ ] 普通设备主要只修改对应设备族文件、声明和 builtin registry。
- [ ] 没有用专属逻辑重复现有 Collector/Mapper/字段模型能力。
- [ ] 已与真实设备报文核对工程量、无效值、enum/bit、关键数据、实时和历史行为。
- [ ] 如有写命令，已在安全条件下完成真实设备验证并确认失败反馈。
