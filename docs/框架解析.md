# 运行架构与产品边界

本文描述当前代码的职责、主调用链和必须长期保持的契约。用户操作与部署入口见仓库根 [`README.md`](../README.md)，开发和发布细节见本目录其他文档。

## 进程职责

```text
Browser / Chromium Kiosk
        │ HTTP
        ▼
edge-web (Go)
        │ Unix Domain Socket + length frame + JSON
        ▼
edge-controller (C++)
        │
        ├── SQLite
        ├── Modbus RTU / TCP southbound
        ├── MQTT northbound
        ├── Modbus TCP server northbound
        └── Linux network / time / update commands
```

`edge-controller` 是业务配置和运行态的唯一所有者。`edge-web` 负责登录、权限、HTTP 输入边界、页面聚合和输出，不直接打开业务数据库或现场通信设备。Web 与 controller 同版本发布，因此生产链只保留当前 IPC method；数据库和应用升级所需的持久化兼容是另一条必须保留的边界。

## C++ 分层

```text
interface
  -> BackendService / service
  -> datastore / polling / runtime
  -> collect / device model / protocol / channel / platform
```

- `interface` 负责 UDS 帧、JSON 转换、method 分发和协议错误，不定义业务规则。
- `BackendService` 是 IPC 的稳定门面，拥有组件生命周期和跨组件协调锁。
- `service` 承担配置应用、运行态重建、系统设置、查询聚合和告警协调。
- `datastore` 是 SQLite schema、事务和查询的唯一实现位置。
- `collect` 把已校验配置编译为读取计划，执行 Modbus 读写并产生统一点位结果。
- `channel` 与 `protocol` 隔离串口/TCP 生命周期、超时和 Modbus 帧语义。

耗时的通道停止、线程 join 和外部系统命令不得在全局服务独占锁内等待。运行态页面尽量读取内存快照；配置与历史数据才进入 SQLite。

## IPC 契约

IPC 使用 Unix Domain Socket。每个消息由 4 字节大端长度头和 JSON payload 组成，单帧最大 8 MiB。

- Go 默认最多并发 4 个后端调用，多余调用在可取消信号量处等待。
- C++ 使用固定 worker，不为每个连接创建无限线程；过载返回 `server_busy`。
- 等待并发槽、connect、read 和 write 共享同一个请求 deadline。
- 每次调用使用独立连接，controller 重启后下一次请求可重新连接。
- 普通响应必须匹配请求 ID；读取请求尚未进入 worker 前的连接级过载可返回 `id:null`。
- 有副作用的请求发送后若响应超时，执行结果可能不确定，客户端不得自动重试。

method 名、参数含义、response schema 和错误语义是跨语言契约。内部文件拆分不能改变这些字段。

## 采集与运行态

通道可使用 Modbus RTU 或 Modbus TCP。主站配置引用设备类型并给出起始寄存器、设备数量、轮询周期和从站地址；设备实例由配置推导。

设备类型包含一个或多个读取区块。区块支持 FC03/FC04，字段支持：

- `uint16`、`int16`、`uint32`、`int32`、`float32`；
- ABCD、BADC、CDAB、DCBA 对应的字节序与字序；
- 单 bit、枚举、倍率、偏置和精度；
- 相等、范围和阈值类无效规则；
- 摘要、历史和实时展示策略。

读取计划在配置应用时生成。轮询热路径复用静态配置和映射结果，只把本轮寄存器值、质量和时间戳送往 runtime、history、alarm、MQTT 与 Modbus TCP register bank。

通讯质量描述 transport 是否成功；数据质量描述字段是否能可信使用。二者不能互相覆盖。无效字段不会作为有效历史样本或可信北向值发布。

## 历史、事件与告警

板端数据库位于 `/opt/edge-controller/data`：

```text
edge-config.db    配置、用户、设备类型、告警规则和北向映射
edge-history.db   原始、小时和日历史
edge-events.db    系统、通讯和告警事件
```

写连接使用 WAL、`busy_timeout=5000` 和有界事务。当前 schema 基线为配置库 `user_version=9`、历史库 `user_version=1`、事件库 `user_version=1`。代码只接受空库或对应当前结构；旧结构必须由目标发布版本明确提供的迁移流程处理，不能通过删除现场数据库规避兼容问题。

历史链路按采样策略进入原始表，并定期维护小时/日聚合。系统时间早于可信下限时暂停历史写入；显著时间跳变会重置尚未落库的 bucket，防止新旧时间轴混合。

告警规则按设备点位运行，状态机包含 pending、active、acknowledged 和 recovered。触发、确认、恢复均形成事件；MQTT 发布在本地事件持久化成功后 best-effort 执行。

## MQTT 与 Modbus TCP 北向

MQTT 使用 libmosquitto，支持 TLS 和双向证书。固定 topic 为：

```text
{topic_prefix}/{node_id}/status
{topic_prefix}/{node_id}/realtime
{topic_prefix}/{node_id}/event
{topic_prefix}/{node_id}/alarm
```

对应 schema 为 `edge.status.v1`、`edge.realtime.v1`、`edge.event.v1` 和 `edge.alarm.v1`。Broker 断开、TLS 错误或 publish 失败不能阻塞南向采集。

Modbus TCP 北向服务拥有独立监听配置、客户端上限、空闲超时和 register bank。字段值与质量地址在新 bank 完整构造后原子切换，避免配置重载暴露半更新映射。

## Web 与前端生命周期

Go HTTP 层负责 session、角色授权、CSRF、请求体上限和结构化错误。页面 service 对一次页面渲染所需数据进行聚合，避免模板或 handler 自行发散 IPC。

前端没有 Node 构建依赖。`app-core.js` 提供通用 DOM、toast、弹窗、表单和请求能力；`app-navigation.js` 管理同源软导航、页面级请求和事件生命周期；业务脚本仅在对应页面加载。大体积虚拟键盘词库只应在板端触摸输入场景按需加载。

页面离开时必须取消请求、定时器和监听器，并关闭弹窗、菜单、键盘和滚动锁。代码必须兼容产品当前板端 Chromium，不使用仅为现代化而引入的新语法。

## 资源与安全边界

- 普通 JSON 请求通常限制为 64 KiB，批量/设备类型请求可放宽到 512 KiB。
- 配置导入最大 2 MiB；应用升级上传最大 256 MiB。
- CSV 与诊断 ZIP 使用固定缓冲流式输出，浏览器取消会终止后续读取。
- session、登录失败记录、IPC 并发、Modbus 客户端和升级暂存均有容量上限。
- 密码使用带随机 salt 的 PBKDF2-HMAC-SHA256；所有状态修改请求必须校验 CSRF 与角色。
- MQTT 密码和证书内容不得进入页面、诊断快照或日志。
- 当前 Web 面向受控内网。若跨不可信网络部署，应由网关提供 HTTPS 和访问隔离。

## 升级一致性

Update Manager 是高风险独立边界。Web 只写受限 upload 目录；root manager 重新检查文件类型、权限、大小、MANIFEST、版本、架构和可选/强制签名，然后由独立 systemd job 执行。

升级状态、backup 完成标记、原子切换、health check、开机恢复和回滚顺序不得由普通代码整理改变。业务服务带恢复门禁，处于不安全中间状态时不能绕过 recovery manager 启动。
